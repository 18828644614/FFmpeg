## 第一部分：先建立计算机模型

### 1. 数据、程序、文件和内存

计算机只处理数字。文本、图片、音乐和视频最终都会变成一串 0 和 1。为了方便，人们用不同的规则解释这串数字：同一串字节如果按文本解释可能是字符，按 PCM 解释可能是声音，按 JPEG 规则解释可能是图片。

- **位（bit）**：只能是 0 或 1，常写作 `b`。
- **字节（byte）**：通常由 8 个 bit 组成，常写作 `B`。`1 KB` 在文件大小语境中常近似为 `1024 B`，网络速率中的 `kbps` 通常按 `1000 bit/s` 计算，看到单位时要确认语境。
- **文件**：保存在磁盘上的一串字节，加上文件名、路径和元数据。
- **程序**：一组告诉 CPU 如何处理数据的指令。C++ 源代码只是人能读的文本，编译后才会成为 Windows 可执行文件。
- **内存**：程序运行时使用的临时空间。程序退出后，普通内存中的内容不会自动成为文件。

一个最容易混淆的例子：把 `video.mp4` 改名为 `video.txt` 不会把视频转换成文本。改名只改变文件名，文件内部的字节和格式没有变化。

### 2. 从源代码到正在运行的程序

一个简单的 C++ 项目大致经历以下过程：

```text
main.cpp
   | 预处理：展开头文件和宏
   v
编译：每个 .cpp 变成目标文件 .obj
   |
   v
链接：把多个 .obj 和 .lib 合并成 .exe
   |
   v
运行：Windows 加载 .exe，并在需要时加载 .dll
```

这里的文件角色不同：

- `.h` / `.hpp`：声明，告诉编译器“有哪些函数、类型和常量”。
- `.cpp`：实现，包含真正的代码。
- `.obj`：编译后的中间目标文件。
- `.lib`：链接阶段使用的库；动态库的导入库也可能使用这个扩展名。
- `.dll`：程序运行时加载的动态库。
- `.exe`：可执行程序。

因此，下面三种错误发生在不同阶段：

| 错误 | 发生阶段 | 含义 |
|---|---|---|
| `fatal error C1083: Cannot open include file` | 编译 | 编译器找不到头文件 |
| `LNK1104: cannot open file 'avformat.lib'` | 链接 | 链接器找不到库文件或架构不匹配 |
| `0xc0000135` / 找不到 DLL | 运行 | Windows 找不到程序依赖的动态库 |

先判断阶段，再排错，效率会比反复重装高得多。

### 3. 进程、线程和资源

- **进程**：一个正在运行的程序，以及它拥有的内存、文件句柄和其他资源。
- **线程**：进程中的一条执行路线。一个进程可以有多个线程。
- **资源**：文件、内存、网络连接、解码器上下文等都属于需要申请和释放的资源。

FFmpeg 程序经常同时持有文件、格式上下文、解码器上下文、数据包和帧。每申请一个资源，都要确认谁负责释放它。C++ 中用 RAII 和智能指针管理资源，可以减少“忘记释放”和“释放两次”的错误；具体语法见 [[01-前置基础/C++基础]] 和 [[04-C++调用FFmpeg/错误处理与资源生命周期]]。

## 第二部分：只学本章用得到的 C++

### 1. 变量、类型和函数

变量是带类型的存储位置。`int` 适合一般整数，`double` 适合小数，`std::string` 适合文本。FFmpeg 中还会遇到 `int64_t`，它表示明确为 64 位的整数，常用来保存时间戳、字节数和样本数。

```cpp
#include <cstdint>
#include <iostream>

int main() {
    const int sample_rate = 48000;
    const std::int64_t sample_count = 96000;
    const double seconds = static_cast<double>(sample_count) / sample_rate;

    std::cout << "seconds = " << seconds << "\n";
    return 0;
}
```

注意 `sample_count / sample_rate` 如果两个变量都是整数，结果会先进行整数除法；转换成 `double` 后才会保留小数。

### 2. 指针、数组和所有权

指针保存一个内存地址。FFmpeg 的 C API 经常使用指针，因为函数需要返回大块数据，或需要修改调用者提供的对象。

- `T* p`：`p` 可能指向一个 `T`，也可能是空指针 `nullptr`。
- `p->field`：访问指针指向的对象成员，前提是 `p` 不为空。
- `data[i]`：访问数组第 `i` 个元素。
- **所有权**：谁申请，谁负责释放，或明确把释放责任转交给另一个对象。

下面的代码只演示“先检查再使用”：

```cpp
int* value = nullptr;

if (value != nullptr) {
    // 只有确认不是空指针后，才能解引用 *value。
    std::cout << *value << "\n";
}
```

不要把 `nullptr` 当成“0 号数据”。它表示“这里没有有效对象”。FFmpeg 函数返回空指针时，通常意味着查找失败或申请失败。

### 3. 错误码和清理路径

FFmpeg 的许多函数返回 `0` 或正数表示成功，负数表示失败。C++ 示例通常会在失败分支中关闭已经打开的资源：

```cpp
int ret = do_something();
if (ret < 0) {
    close_resource();
    return 1;
}
```

不要只打印“失败”，要把错误码转换成人能读的文字。后面的 `media_info.cpp` 会使用 `av_strerror` 完成这件事。

## 第三部分：数字音频

### 1. 从连续声音到数字数据

现实中的声音是随时间连续变化的压力波。计算机不能无限精确地保存连续曲线，所以每隔固定时间测量一次声音，这一步叫**采样（sampling）**。

一次采样得到一个数值。连续的一秒声音会变成许多整数或浮点数，这些数按约定排列起来就是数字音频数据。

### 2. 采样率（sample rate）

采样率表示每秒采集多少个样本，单位是 Hz。`48000 Hz` 表示每秒 48000 个样本。采样率越高，时间方向的细节越多，但原始数据量也越大。

在理想条件下，采样率至少要大于声音最高频率的两倍，这个结论称为奈奎斯特采样条件。实际工程还会使用低通滤波器，所以不要把“采样率越高一定越好”当成绝对规则。

### 3. 位深（bit depth）和量化

采样得到的真实数值通常不是整数，计算机需要把它四舍五入到有限个等级，这一步叫**量化**。位深决定一个样本有多少个可表示等级：

- 8 bit：每个样本有 `2^8 = 256` 个等级。
- 16 bit：有 `2^16 = 65536` 个等级，PCM 音频中非常常见。
- 24 bit：等级更多，常用于录音和制作场景。

位深越高，量化误差通常越小，但每个样本占用的字节也越多。

### 4. 声道（channel）和交错存储

声道是独立的一路音频信号。单声道是 1 路，立体声是左、右 2 路，5.1 则包含更多声道。

常见存储方式有两种：

- **交错（packed/interleaved）**：立体声按 `L0, R0, L1, R1...` 排列。
- **分平面（planar）**：左声道和右声道放在不同缓冲区。

后面看到 FFmpeg 的 `AVSampleFormat` 时，名称带 `p` 往往表示 planar，例如 `fltp`；不带 `p` 的格式通常表示 packed，例如 `flt`。确切含义仍应以格式文档和 API 返回值为准。

### 5. PCM、音频帧和码率

**PCM** 是未压缩的脉冲编码调制数据。它只描述样本值，不包含“采样率是多少、声道数是多少”的自解释信息，所以播放裸 PCM 时必须另外提供参数。

未压缩 PCM 的近似码率计算公式：

```text
码率（bit/s）= 采样率 × 位深 × 声道数
```

例如，`48000 Hz`、`16 bit`、双声道：

```text
48000 × 16 × 2 = 1,536,000 bit/s
= 192,000 byte/s
```

FFmpeg 中的**音频帧（audio frame）**不是“视频画面”。它通常包含一小段连续音频样本，例如 1024 个样本。样本数、声道布局、采样格式和时间戳共同描述这段音频。

## 第四部分：数字视频

### 1. 像素、分辨率和帧

视频可以先理解为“按时间顺序排列的一张张图片”：

- **像素（pixel）**：图片中一个最小的颜色单元。
- **分辨率（resolution）**：一帧有多少列和多少行，例如 `1920x1080`。
- **帧（frame）**：某一时刻的一张画面。
- **帧率（frame rate）**：每秒显示多少帧，例如 24、30、60 fps。

未压缩 RGB 视频的单帧数据量大约是：

```text
宽 × 高 × 每像素字节数
```

`1920x1080`、RGB24（每像素 3 字节）的一帧约为 5.93 MiB；30 fps 时，原始数据约 177.8 MiB/s。这个数量说明了为什么视频需要压缩。

### 2. 像素格式（pixel format）

像素格式规定颜色分量如何排列、每个分量占多少位、数据是否分平面。常见格式：

- `rgb24`：每个像素按红、绿、蓝三个 8 bit 分量排列。
- `yuv420p`：Y、U、V 分开存储，色度分辨率低于亮度，视频编码中非常常见。
- `nv12`：Y 平面加交错的 UV 平面，硬件视频路径中常见。

不要只看 `1920x1080` 就认为两张图片可以直接逐字节比较；分辨率相同但像素格式不同，内存布局可能完全不同。

### 3. 颜色空间和 YUV 的直觉

RGB 直接表示红、绿、蓝；YUV（工程中也会遇到 YCbCr 这个更准确的说法）把亮度和色度分开。人眼对亮度细节更敏感，对色度细节相对不敏感，因此可以降低色度分辨率来节省数据量。

`4:2:0` 表示色度采样比亮度稀疏，不能简单理解成“只有 4 个像素”。转换 RGB 与 YUV 时还涉及矩阵、色域、范围（limited/full range）等信息，这些错误会造成画面偏灰、偏色或亮度不对。

### 4. 帧率、码率和质量

- 帧率主要影响时间上的运动是否平滑。
- 分辨率主要影响空间细节。
- 码率表示每秒使用多少压缩后数据，通常用 `bit/s`、`kbps` 或 `Mbps` 表示。
- 编码器会利用帧内和帧间的相似性压缩视频；因此压缩后大小不等于“宽 × 高 × 帧数”。

提高帧率、分辨率或质量通常会增加数据量，但实际大小还取决于内容、编码器、码率控制方式和关键帧间隔。

## 第五部分：媒体文件和 FFmpeg 的数据流

### 1. 容器、编码和媒体流

这几个词描述的是不同层次：

- **编码器（encoder）**：把原始音频或视频压缩成编码数据，例如 H.264、HEVC、AAC、Opus。
- **解码器（decoder）**：把编码数据还原成可处理的音频样本或视频像素。
- **容器（container）**：把一个或多个流、时间戳、元数据和索引组织成文件，例如 MP4、MKV、WebM。
- **流（stream）**：容器中的一条连续媒体轨道，例如一条视频流或一条音频流。
- **封装（mux）**：把编码后的多个流写入容器。
- **解封装（demux）**：从容器中读出各条流的数据包。

一个 MP4 文件可能包含一条 H.264 视频流和一条 AAC 音频流。MP4 不是视频编码，H.264 也不是文件扩展名；把这两个层次混在一起会导致很多配置错误。

### 2. 包、帧和处理流水线

在 FFmpeg 中，可以用下面的简化流水线理解播放或转码：

```text
文件
  -> 解封装器 demuxer
  -> AVPacket（编码数据包）
  -> 解码器 decoder
  -> AVFrame（原始音频样本或视频像素）
  -> 处理：缩放、重采样、滤镜、混音
  -> 编码器 encoder
  -> AVPacket（新的编码数据）
  -> 封装器 muxer
  -> 新文件
```

- `AVPacket` 更接近“从文件或网络读到的编码数据块”。一个包可能包含一个完整帧，也可能因为格式而跨越边界。
- `AVFrame` 表示解码后的原始数据，视频帧包含像素，音频帧包含样本。
- “读包”和“解码出帧”不是一一对应关系。尤其视频存在 B 帧时，解码顺序和显示顺序可能不同。

### 3. FFmpeg 的主要组件

| 组件 | 作用 | 本章要记住的对象 |
|---|---|---|
| libavformat | 读写容器、解封装、封装 | `AVFormatContext`, `AVStream` |
| libavcodec | 编解码器 | `AVCodec`, `AVCodecContext`, `AVCodecParameters` |
| libavutil | 基础类型、时间、错误、数学 | `AVRational`, `av_rescale_q` |
| libswscale | 视频像素格式和尺寸转换 | `sws_scale` |
| libswresample | 音频采样率、格式、声道转换 | `swr_convert` |
| libavfilter | 滤镜图 | `AVFilterGraph` |

本章的 C++ 示例只需要 `libavformat`、`libavcodec` 和 `libavutil`。解码、像素转换和重采样会在后续主题中展开。

## 第六部分：时间戳和音视频同步

### 1. 为什么需要时间戳

播放器不能只知道“这是第几个包”，还要知道它应该在什么时候显示或播放。时间戳就是给媒体数据附上的时间位置。

- **PTS（presentation timestamp）**：显示或播放时间。
- **DTS（decoding timestamp）**：送入解码器的时间。
- **duration**：这一包或这一帧持续多长时间。

有 B 帧时，解码器可能需要先解码后面的参考帧，导致 DTS 和 PTS 不同。入门阶段记住：播放器以 PTS 安排呈现，解码器可能按 DTS 接收数据。

### 2. time base 不是时间戳

FFmpeg 通常用 `AVRational` 表示时间基：

```text
实际秒数 = 时间戳 × time_base.num / time_base.den
```

如果 `time_base = 1/1000`，时间戳 `1500` 表示 1.5 秒；如果 `time_base = 1/90000`，同一个数字表示约 16.67 毫秒。时间戳离开自己的 time base 后没有独立含义。

不要直接把两个不同流的时间戳相减。应先使用 `av_rescale_q` 转换到相同的时间基，再比较或计算。

### 3. 音视频同步的直觉

同步的目标是让同一时刻的声音和画面一起呈现。常见做法是选择一个主时钟（音频时钟、视频时钟或外部时钟），比较当前帧的 PTS 与主时钟的差值，再决定等待、丢帧或补偿。完整同步策略见 [[05-解封装与解码/音视频同步基础]] 和 [[08-播放器开发/音视频同步实现]]。

## 第七部分：FFmpeg 内存和数据布局

### 1. `data[]`、`linesize[]` 和平面

`AVFrame` 的 `data[]` 是若干个数据指针，`linesize[]` 是每个平面一行占用的字节数。

视频 `yuv420p` 通常有三个平面：

```text
data[0] -> Y 平面，宽 × 高
data[1] -> U 平面，宽/2 × 高/2
data[2] -> V 平面，宽/2 × 高/2
```

真实分配的 `linesize` 可能大于可见宽度，因为库会为对齐和 SIMD 优化预留填充。遍历图像时不能假设 `linesize == width`。

音频 frame 也可能是 packed 或 planar。读取样本前要查看 `sample_fmt`、`ch_layout`、`nb_samples` 和 `linesize`，不能凭文件扩展名猜内存布局。

### 2. 缓冲区大小和生命周期

常见生命周期顺序如下：

```text
申请 AVFormatContext
  -> 打开输入
  -> 读取流信息
  -> 反复申请/复用 AVPacket 和 AVFrame
  -> 结束后释放 packet/frame
  -> 关闭输入并释放 format context
```

FFmpeg 不同对象有专用释放函数，例如 `av_packet_free`、`av_frame_free`、`avcodec_free_context`、`avformat_close_input`。不要混用 `delete` 或 `free` 去释放 FFmpeg 分配的对象。

### 1. 验证 PowerShell 和 FFmpeg

打开 PowerShell，执行：

```powershell

```

如果命令未找到，需要安装 FFmpeg，并把包含 `ffmpeg.exe` 和 `ffprobe.exe` 的 `bin` 目录加入 PATH。修改 PATH 后要重新打开 PowerShell。不要把 `include` 或 `lib` 目录加入 PATH；运行时需要的是 DLL 所在的目录。

### 2. 开发包的目录结构

C++ 编译 FFmpeg 程序通常需要一个开发包，结构类似。本章示例以 FFmpeg 5.0 及以上为前提，因为代码使用了 `AVChannelLayout` 的 `ch_layout` 字段；如果使用更旧的 FFmpeg，需要按对应版本改用旧的声道字段。

```text
C:\ffmpeg\
  include\libavformat\avformat.h
  include\libavcodec\avcodec.h
  include\libavutil\avutil.h
  lib\avformat.lib
  lib\avcodec.lib
  lib\avutil.lib
  bin\avformat-*.dll
  bin\avcodec-*.dll
  bin\avutil-*.dll
```

具体 DLL 名称会随版本变化。编译器需要 `include`，链接器需要 `lib`，程序运行时需要 `bin`。这三个目录的作用不同。

### 3. 架构和版本必须一致

Windows 项目常见的架构有 x64 和 x86。x64 的程序不能直接加载 x86 的 FFmpeg DLL，反过来也不行。编译器、FFmpeg 开发包、DLL 和 CMake 生成器要保持一致；初学者建议全程使用 x64。

### 实验 2：用 C++ + FFmpeg 读取媒体信息

#### 2.1 `media_info.cpp`

把下面内容保存为 `media_info.cpp`：

```cpp
#include <iomanip>
#include <iostream>
#include <string>

extern "C" {
#include <libavcodec/avcodec.h>
#include <libavcodec/codec_par.h>
#include <libavformat/avformat.h>
#include <libavutil/error.h>
#include <libavutil/mathematics.h>
#include <libavutil/rational.h>
}

std::string ffmpeg_error(int code) {
    char buffer[AV_ERROR_MAX_STRING_SIZE]{};
    av_strerror(code, buffer, sizeof(buffer));
    return buffer;
}

const char* media_type_name(AVMediaType type) {
    switch (type) {
    case AVMEDIA_TYPE_VIDEO:
        return "video";
    case AVMEDIA_TYPE_AUDIO:
        return "audio";
    case AVMEDIA_TYPE_SUBTITLE:
        return "subtitle";
    default:
        return "other";
    }
}

int main(int argc, char* argv[]) {
    if (argc != 2) {
        std::cerr << "Usage: media_info.exe <input-file>\n";
        return 2;
    }

    const char* input_path = argv[1];
    AVFormatContext* format = nullptr;

    int ret = avformat_open_input(&format, input_path, nullptr, nullptr);
    if (ret < 0) {
        std::cerr << "Cannot open input: " << ffmpeg_error(ret) << "\n";
        return 1;
    }

    ret = avformat_find_stream_info(format, nullptr);
    if (ret < 0) {
        std::cerr << "Cannot read stream information: " << ffmpeg_error(ret) << "\n";
        avformat_close_input(&format);
        return 1;
    }

    av_dump_format(format, 0, input_path, 0);

    std::cout << "\nContainer: "
              << (format->iformat && format->iformat->long_name
                      ? format->iformat->long_name
                      : "unknown")
              << "\n";

    if (format->duration != AV_NOPTS_VALUE) {
        std::cout << std::fixed << std::setprecision(3)
                  << "Duration: "
                  << static_cast<double>(format->duration) / AV_TIME_BASE
                  << " s\n";
    } else {
        std::cout << "Duration: unknown\n";
    }

    std::cout << "Streams: " << format->nb_streams << "\n";

    for (unsigned int i = 0; i < format->nb_streams; ++i) {
        const AVStream* stream = format->streams[i];
        const AVCodecParameters* parameters = stream->codecpar;

        std::cout << "\n[Stream " << i << "]\n"
                  << "type: " << media_type_name(parameters->codec_type) << "\n"
                  << "codec: " << avcodec_get_name(parameters->codec_id) << "\n"
                  << "time_base: " << stream->time_base.num << "/"
                  << stream->time_base.den << "\n";

        if (parameters->codec_type == AVMEDIA_TYPE_VIDEO) {
            std::cout << "size: " << parameters->width << "x"
                      << parameters->height << "\n";
            if (stream->avg_frame_rate.den != 0) {
                std::cout << "avg_fps: " << std::fixed << std::setprecision(3)
                          << av_q2d(stream->avg_frame_rate) << "\n";
            }
        } else if (parameters->codec_type == AVMEDIA_TYPE_AUDIO) {
            std::cout << "sample_rate: " << parameters->sample_rate << "\n"
                      << "channels: " << parameters->ch_layout.nb_channels << "\n";
        }

        if (stream->duration != AV_NOPTS_VALUE) {
            const double seconds = stream->duration * av_q2d(stream->time_base);
            std::cout << "stream_duration: " << std::fixed
                      << std::setprecision(3) << seconds << " s\n";
        }
    }

    avformat_close_input(&format);
    return 0;
}
```

代码做了四件事：打开输入文件、读取流信息、打印每条流的元数据、关闭输入。它还没有解码，所以不会输出像素或声音样本。`AVFormatContext` 管整个输入，`AVStream` 描述其中一条流，`AVCodecParameters` 描述这条流使用的编码参数。

### 实验 3：理解 time base 的换算

保存为 `timestamp_demo.cpp`：

```cpp
#include <cstdint>
#include <iostream>

extern "C" {
#include <libavutil/mathematics.h>
#include <libavutil/rational.h>
}

int main() {
    const AVRational milliseconds = {1, 1000};
    const AVRational video_time_base = {1, 90000};
    const std::int64_t timestamp_in_ms = 1500;

    const std::int64_t converted = av_rescale_q(
        timestamp_in_ms, milliseconds, video_time_base);

    std::cout << "1500 ms = " << converted
              << " ticks in a 1/90000 time base\n";
    std::cout << "back to milliseconds = "
              << av_rescale_q(converted, video_time_base, milliseconds)
              << "\n";
    return 0;
}
```

编译时只需要链接 `avutil`：

```powershell
cl /std:c++17 /EHsc timestamp_demo.cpp `
  /I C:\ffmpeg\include `
  /link /LIBPATH:C:\ffmpeg\lib avutil.lib
$env:PATH = "C:\ffmpeg\bin;$env:PATH"
.\timestamp_demo.exe
```

预期看到 `1500 ms = 135000 ticks`，再换回毫秒仍是 `1500`。这个实验的重点是：换算时同时传入原时间基和目标时间基，而不是手写容易溢出或取整错误的乘除法。

### 实验 4：用 C++ 生成裸 PCM，再让 FFmpeg 解释它

保存为 `generate_pcm.cpp`：

```cpp
#include <cmath>
#include <cstdint>
#include <fstream>
#include <iostream>

int main() {
    constexpr int sample_rate = 48000;
    constexpr int seconds = 2;
    constexpr double frequency = 440.0;
    constexpr double pi = 3.14159265358979323846;

    std::ofstream output("tone.pcm", std::ios::binary);
    if (!output) {
        std::cerr << "Cannot create tone.pcm\n";
        return 1;
    }

    for (int n = 0; n < sample_rate * seconds; ++n) {
        const double time = static_cast<double>(n) / sample_rate;
        const double wave = std::sin(2.0 * pi * frequency * time);
        const auto sample = static_cast<std::int16_t>(wave * 30000.0);
        output.write(reinterpret_cast<const char*>(&sample), sizeof(sample));
    }

    std::cout << "Generated 2 seconds of mono s16 PCM.\n";
    return 0;
}
```

编译并用 FFmpeg 给裸 PCM 补上参数，再封装成 WAV：

```powershell
cl /std:c++17 /EHsc generate_pcm.cpp
.\generate_pcm.exe
ffmpeg -f s16le -ar 48000 -ac 1 -i .\tone.pcm .\tone.wav
ffprobe -hide_banner .\tone.wav
```

命令中的参数含义：

- `-f s16le`：输入是 signed 16-bit little-endian PCM。
- `-ar 48000`：采样率 48000 Hz。
- `-ac 1`：输入有 1 个声道。
- `-i`：输入文件。

裸 PCM 没有文件头，FFmpeg 如果不知道这些参数，就无法正确解释字节。WAV 在容器中保存了这些基本信息，所以播放器通常可以直接打开。

## API / 工具 / 配置速查

### C++ 与 FFmpeg API

| API 或类型 | 用途 | 初学者要注意 |
|---|---|---|
| `avformat_open_input` | 打开输入容器 | 成功后要用 `avformat_close_input` 关闭 |
| `avformat_find_stream_info` | 读取流信息 | 网络或损坏文件可能较慢或失败 |
| `av_dump_format` | 打印格式和流摘要 | 适合调试，不替代自己的业务逻辑 |
| `AVFormatContext` | 输入/输出容器上下文 | 负责整个文件或媒体源 |
| `AVStream` | 一条音频、视频或字幕流 | 每个流有自己的 time base |
| `AVCodecParameters` | 编码参数 | 描述 codec、宽高、采样率等 |
| `avcodec_get_name` | codec id 转名称 | 只负责名称，不会创建解码器 |
| `av_q2d` | `AVRational` 转 `double` | 分母为 0 时要先判断 |
| `av_rescale_q` | 在两个时间基之间换算 | 优先使用它处理时间戳 |
| `av_strerror` | 错误码转文字 | 输出后仍要保留原始错误码 |

## 常见错误与排查顺序

### 1. `ffmpeg is not recognized`

先执行 `where.exe ffmpeg`。如果没有输出，说明当前 PATH 中没有 `ffmpeg.exe`。把 `bin` 目录加入用户 PATH，关闭并重新打开 PowerShell，再执行 `ffmpeg -version`。临时验证也可以使用绝对路径：

```powershell
& "C:\ffmpeg\bin\ffmpeg.exe" -version
```

### 2. `Cannot open include file: libavformat/avformat.h`

这是编译阶段错误。检查：

1. `C:\ffmpeg\include\libavformat\avformat.h` 是否真的存在。
2. CMake 的 `FFMPEG_ROOT` 是否指向开发包根目录，而不是 `bin`。
3. 是否重新配置了 build 目录：`cmake -S . -B build ...`。

### 3. `LNK1104 cannot open avformat.lib`

这是链接阶段错误。检查 `C:\ffmpeg\lib\avformat.lib` 是否存在，`/LIBPATH` 或 CMake 的 `lib` 路径是否正确，并确认库与编译器、CPU 架构匹配。

### 4. 程序启动时提示缺少 `avformat-*.dll`

这是运行阶段错误。把 FFmpeg 的 `bin` 加入当前进程 PATH，或把需要的 DLL 复制到 `.exe` 同目录。开发阶段推荐临时设置 PATH，避免把 DLL 散落在项目中：

```powershell
$env:PATH = "C:\ffmpeg\bin;$env:PATH"
```

### 5. `Invalid data found when processing input`

常见原因：文件不是它声称的格式、下载不完整、扩展名只是改名、输入参数写错、路径指向了错误文件。用 `ffprobe -hide_banner` 单独检查；如果是裸 PCM，必须提供 `-f`、`-ar`、`-ac` 等输入参数。

如果实验 1 报 `Unknown encoder 'libx264'`，说明当前 FFmpeg 构建没有包含该编码器。可以换用包含 x264 的构建，或临时把 `-c:v libx264` 改成 `-c:v mpeg4`；本实验重点是生成可检查的测试文件，不依赖某一个视频编码器。

### 6. 路径含空格导致打开失败

把整个路径放在双引号中：

```powershell
.\media_info.exe "C:\Media Files\sample.mp4"
```

在 C++ 中不要把用户输入的路径按空格拆分；`argv[1]` 只在调用方正确加引号时才能得到完整路径。

### 7. `Duration: unknown` 或时间戳是 `AV_NOPTS_VALUE`

实时流、损坏文件、某些特殊容器可能没有可靠的总时长。`AV_NOPTS_VALUE` 不是一个可以显示给用户的普通时间，它表示“没有可用时间戳”。代码必须先判断，再进行换算。

### 8. 输出的声道数或像素格式和预期不一致

不要只根据文件扩展名猜参数。使用 `ffprobe -show_streams`，在 API 中查看 `AVCodecParameters` 和解码后 `AVFrame` 的实际字段。编码流的参数和解码后的内存格式可能不同，必要时要经过重采样或像素格式转换。

### 9. 只释放了一个对象，程序仍然崩溃

检查是否：

- 使用了错误的释放函数。
- 在 `avformat_close_input` 后继续访问 `format` 或 `stream`。
- 把 `AVPacket` 或 `AVFrame` 的数据指针保存到对象释放之后。
- 在异常或早期 `return` 路径漏掉了清理。

先画资源生命周期图，再考虑优化。不要用“程序马上结束了，应该没关系”解释未定义行为。
